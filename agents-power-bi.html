Where I use agents in a Power BI repo

August 2026 · Martin Padilla Schekaiban · 5 min read

A lot of the work around a Power BI report happens outside the canvas. Measures need reviewing, field references need checking, and the same formatting change may need applying across several pages. Those are the jobs where I reach for a coding agent.

Saving a project as PBIP makes that possible. The semantic model and report definitions are available as text, so I can put them in Git and review an agent's changes alongside my own. It doesn't remove the need to open the report. It does make some repetitive changes much easier to inspect before I do.

Start with an existing measure

For DAX work, I want the agent to read the relevant part of the model before it writes anything. A request such as “add on-time percentage by carrier” leaves too much unspecified. Which date? Do undelivered shipments count? Is there already a measure that the rest of the report uses?

Without that context, I spend the review correcting table names and replacing calculations that duplicate existing measures. With model access, the first response can be a reference to the current definition and a proposed change. That's something I can review against the requirement.

I usually ask it to show the existing expression, explain what it would reuse, and provide a small query for checking the result. The query still needs review: a measure can return plausible values while using the wrong date relationship or denominator. The MCP article covers the model-access side in more detail.

Repetitive edits are worth the setup

Applying the same formatting rule to a group of visuals is a useful example. In a PBIR report, that can mean editing a separate JSON definition for each visual. Doing the first one by hand establishes the change; asking an agent to apply that specific diff to the remaining matching visuals saves the repetitive part.

The word “matching” matters. I don't want a broad replacement across every object with a similar property name. Different visual types, or visuals created by different Desktop versions, can store equivalent settings differently. I ask for a list of files it plans to touch and check that list before letting the edit expand.

Afterward, I look for unexpected changes in the diff and open representative pages in Desktop. A valid JSON file proves very little about whether a report still looks right.

Layout and identifiers need separate checks

Moving a visual means changing coordinates, but deciding whether it fits requires seeing the page. A bounds check can catch a visual outside the canvas. It won't tell me that a label is cramped, that the spacing looks uneven, or that an overlap is intentional. For layout work, I keep the change small and inspect the rendered report.

Identifiers are a different problem. Copying a block of report or model text can also copy its identity fields. Whether an identifier should be preserved, regenerated, or referenced elsewhere depends on the object. Treating every GUID as disposable is just as risky as copying all of them.

I ask for identity fields to be called out explicitly during review. New objects need the appropriate fresh identifiers; existing objects generally need to keep theirs. Repository checks for duplicate identifiers and broken bindings help here, followed by opening and validating the project in the tools that consume it.

Documentation, with references

An agent is useful for the first pass through a large set of definitions: which measures refer to a column, what a query filters out, or where a report gets a field. I want that output to include file paths and expressions, not just a summary that sounds reasonable.

Renaming a column is a good test of this. Searching the local model may find the DAX references but miss a downstream report or a consumer outside the repository. I treat the result as a list of references found within a stated scope, not proof that nothing else depends on it.

For SQL documentation, I also use a small parser to extract structure before writing a description. That gives the explanation something concrete to refer to. Descriptions of business meaning still need someone who knows the report.

What I keep outside the coding task

A local repository doesn't contain refresh history, gateway state, or the credentials configured in the service. If a refresh fails, I start with the actual error and the service logs. An agent can help interpret an approved, sanitised excerpt, but a guess based only on the project files is not much use.

I also keep the modelling decision with the person responsible for the report. An agent can point out repeated business keys; it can't establish whether the business wants current state or month-end history. That distinction is central to the snapshot example.

My preferred handoff is fairly ordinary: a short description of the requested change, the files changed, the checks that ran, and anything that remains unverified. If a check wasn't run, I want it listed as such. That makes it easier to decide what to review myself before publishing.
