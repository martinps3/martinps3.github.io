I work with Snowflake tables that engineering has already prepared. My part is writing the reporting SQL: joining those tables, choosing the grain, and checking the dataset before it reaches Power BI or an RDL report. This tool compares the result before a join with the result after it. It gives me a short list of keys to investigate instead of just two grand totals.

Why I check more than the distinct count

In the first example, the baseline has three shipments totalling 400. Shipment 101 carries a charge of 120. Joining its two event records repeats that charge, so the joined result totals 520 even though it still contains three distinct shipments.

The “same total, different amounts” example catches a different mistake: one shipment gains 30 and another loses 30. A grand-total comparison passes. The per-key comparison doesn't. Both examples are made-up data, not claims about a particular client incident.

Using it with a reporting query

Export the key and an optional amount from your base query, then export those same fields from the query with the join added. Keep the date range, parameters, business scope and data cutoff aligned. If the ETL output changed between exports, that difference needs investigating too; the tool cannot attribute every change to the join.

Choose the columns that identify one intended report row. That might be a shipment ID, or a shipment ID together with a charge-line ID. If the baseline already repeats that key, the tool calls it out instead of certifying the comparison. Don't add extra columns merely to make duplicates disappear: the selected key should mean something in the report.

Keys are compared as exact text, including case, spaces and leading zeros. Empty key cells are rejected; the text NULL is treated as a literal ID, not a database null. Clean up export-specific null markers before comparing. Amounts are summed using exact decimal arithmetic, with no currency conversion, rounding tolerance or automatic removal of repeated rows.

What I would do with a finding

A repeated shipment key sends me back to the cardinality of the join. If the report needs only an event count, aggregating the events to shipment grain before joining may be appropriate. If it needs event detail, I would keep that grain and avoid summing a repeated shipment charge. Visually grouping the rows in RDL does not repair an inflated dataset total.

Missing keys can come from an inner join or a filter on the right-hand table of a left join. New keys can mean that the two exports don't have the same scope. The useful next step is a short query for those IDs, not an automatic DISTINCT applied to the entire result.

An agent can help follow a long query and suggest checks once I provide the intended grain. The comparison itself is deterministic and doesn't use AI. I still decide whether a change is expected and whether the output is appropriate for the Power BI model or RDL dataset.

Limits and the downloadable SQL

This compares two datasets, not a SQL execution plan. It does not infer the correct grain, detect changes in unselected columns, or prove that a sample represents the full result. Header-only CSV is allowed for an empty result; an empty baseline cannot establish a valid one-row-per-key starting point.

Amounts must have at most 30 integer digits and six fractional digits, using a decimal point without thousands separators, currency symbols or scientific notation. Blank or invalid amounts stop the comparison rather than being silently excluded.

The Snowflake worksheet is a read-only, self-contained version of the shipment example. Replace its two example CTEs with queries from the same reporting scope to check a larger result in your approved environment. It does not connect this page to Snowflake or create any database objects.
