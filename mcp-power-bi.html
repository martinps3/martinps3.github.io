Letting an agent read a Power BI model

The tables and measures it needs to inspect before it writes any DAX.

July 2026 · 6 min read

A common problem with generated DAX is a reference to a column that doesn't exist. The expression looks familiar, and the table name sounds plausible, but it isn't the model you're working on. A less obvious problem is a new measure that almost duplicates one you already have, with a slightly different filter or denominator.

Pasting definitions into a prompt helps for a small change. For repeated work, I'd rather give the assistant a way to look up the definitions it needs. MCP provides a tool interface for that: the assistant calls a server, and the server retrieves model metadata under the permissions it has been given.

Discovery before execution

A tool that only executes DAX leaves the agent with the same naming problem. It needs a small set of discovery tools first. These are example tool names, not a standard Power BI MCP API; the server implementation defines them.

ToolInformation to return
list_tablesTable names, descriptions and hidden flags.
describe_tableColumn names and types, keys, relationships and filter directions.
list_measuresMeasure names, home tables and display folders.
get_measure_daxThe selected expression, format string and description.
run_daxA bounded query result, with execution status and an explicit truncation flag.

I'd keep the first calls small. Listing measure names and folders lets the agent narrow its search before retrieving expressions. Returning every expression in a large model makes it harder to find the relevant definition and uses context unnecessarily. Row counts are optional: depending on how they are obtained, they can turn a metadata request into an expensive data query.

A denominator worth reading

Consider this expression in a synthetic shipment model. DeliveredOnTime is a numeric flag and the fact table contains one row per shipment: 

On Time % =
DIVIDE(
    SUM(Shipment[DeliveredOnTime]),
    COUNTROWS(Shipment)
)

Every visible row contributes to the denominator, including an undelivered shipment if it remains in the filter context. That might match the intended definition, or it might be wrong for a delivered-only KPI. The name “On Time %” doesn't settle it.

I'd ask the agent to retrieve this measure and describe the denominator before proposing a rolling-period version. I also want the relevant relationship: a shipment can have an order date, a pickup date and a delivery date. Finding a table called Date is not enough.

If the agreed definition is the existing measure, and a complete date table has an active relationship to the required shipment date, the new expression can reuse it: 

On Time % L12M =
CALCULATE(
    [On Time %],
    DATESINPERIOD(
        'Date'[Date],
        MAX('Date'[Date]),
        -12,
        MONTH
    )
)

This anchors the window to the maximum date in the current filter context. It does not automatically mean “the last twelve completed months” or “up to today.” Those are separate requirements. Before saving the measure, I would check the date window and compare a few carriers with a query whose numerator and denominator are visible.

The server still has work to do

The Python MCP SDK can expose a lookup with a small wrapper. This is the interface only, not a complete server: find_measure represents the authenticated model lookup and must report missing or ambiguous names explicitly. 

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("powerbi-model")

@mcp.tool()
def get_measure_dax(table_name: str, measure_name: str) -> dict:
    """Read one existing measure; does not change the model."""
    measure = find_measure(table_name, measure_name)
    return {
        "name": measure.Name,
        "table": measure.Table.Name,
        "expression": measure.Expression,
        "format_string": measure.FormatString,
    }

A file-backed implementation can inspect TMDL without connecting to a running model. An XMLA implementation can inspect a deployed model and, with appropriate access, execute queries. XMLA availability depends on the workspace and capacity configuration. These are different capabilities; reading a local definition does not prove that a measure has executed successfully.

Tool descriptions need to state those boundaries. “Read one existing measure” tells the caller more than “get model information.” Errors should distinguish an unavailable model, a missing object and a permission failure rather than returning an empty result for all three.

Permissions and query results

For a first version, I'd expose metadata through the narrowest suitable read-only identity and keep proposed changes in a branch for review. Naming a tool run_dax, or writing “read-only” in its docstring, doesn't enforce that boundary. The model permissions and the operations accepted by the server have to do so.

Query access also means data access. The server identity, any effective-user configuration, and the model's security rules determine what can be returned. A service identity must not accidentally expose data that the person using the assistant is not authorised to see. Metadata can itself be sensitive, so use an approved model and assistant environment.

I would apply a server-side result limit, a query timeout and an explicit indication when rows are omitted. Limiting returned rows does not necessarily limit the work needed to calculate them. Keep credentials and connection strings out of tool responses and logs, including error messages.

What I would review in a change

A useful proposal includes the existing measure it builds on, the relationship it relies on, the new expression, and the query used to check it. If the agent couldn't execute that query, I want to see that stated plainly. A draft that hasn't run is still useful, as long as it isn't presented as a verified result.

The same interface can support documentation and reference searches. I would start with those smaller jobs before allowing model changes, then keep the review process described in my Power BI repository notes.
