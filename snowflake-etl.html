Snowflake → Power BI: incremental refresh

An incremental-refresh setup, with one correction deliberately outside the window.

August 2026 · SQL + Power Query · By Martin Padilla Schekaiban

A shipment arrives in the report on Monday. Its charge is corrected months later. Snowflake has the right value, but will the next Power BI refresh pick it up? That is the question behind this project.

My day-to-day work starts with tables engineering has already prepared. Here I use a small, fictional shipment table to work through the next part: a reporting view, a folding date filter, and an Import model that refreshes recent data without reloading all its history. This is a personal exercise, not a production ETL implementation.

The part I would not skip

The model starts at $2,100. The change script adds a $700 shipment, corrects a recent charge by $50, and corrects the May charge by $80. The source now totals $2,930.

A three-day refresh brings the model to $2,850. It loads the new row and the recent correction, but it does not revisit May. Nothing has failed technically: the policy did exactly what it was told. Reprocessing the affected history brings the model to $2,930.

Making the window 30 days still misses this correction. Making it 150 days catches it, but also re-reads more history. I would choose that window from how far back the business actually corrects records, not just from how fast I want a refresh to finish.

Keep the date filter close to the source

The SQL creates a small source table and a reporting view. The view keeps SHIPPED_AT as a timestamp instead of converting it to formatted text. In Power Query, I navigate to that view and filter it before adding other transformations: 

Filtered = Table.SelectRows(
    Shipments,
    each [SHIPPED_AT] >= RangeStart
      and [SHIPPED_AT] < RangeEnd
)

RangeStart and RangeEnd are case-sensitive Date/Time parameters. Including the start and excluding the end means a record at midnight belongs to one interval, not both. The source uses TIMESTAMP_NTZ with a UTC convention; that convention must also hold for the parameters. NTZ does not store a time zone.

This is a folding-friendly shape, not proof of folding. Before using the policy, I would inspect the queries sent to Snowflake and confirm that both timestamp bounds reach the source. Reading the whole view and filtering it locally can produce the right numbers while defeating the point of incremental refresh. A disabled “View Native Query” option alone is not a conclusive test.

Reproduce it in Desktop and the service

  1. Use a sandbox. Run the setup SQL in your own Snowflake database/schema. It creates project-specific objects and six synthetic records. Use a small warehouse; executing queries and refreshing Power BI can incur Snowflake charges.
  2. Load the reporting view. Create the two Date/Time parameters in Desktop, paste the M query, replace the connection placeholders, and use Import mode. For the fixed-date example, preview 2026-09-21 00:00:00 through 2026-09-24 00:00:00. Expect two initial rows, then three after the change script.
  3. Set the table policy. As an example, store five months and refresh three days. Turn on “Only refresh complete days”; leave real-time DirectQuery and “Detect data changes” off. Use UTC for the service refresh time zone. The browser uses an explicit cutoff and complete date intervals, not the service's current clock.
  4. Publish and establish the baseline. Configure Snowflake credentials in the service and complete the first refresh before applying changes. That first refresh loads the retained history; the narrow Desktop preview is not the historical model.
  5. Apply the changes and reconcile. Run the second SQL script, refresh the model, then compare charges by shipment month as well as the grand total. The setup notes explain how to align the fixed example dates with the day you actually run the service.
The service uses a moving clock.

September 2026 is frozen here to make the example repeatable. A real service policy uses its refresh date and configured time zone. Do not expect these fixed rows to remain inside a three-day window when you run the project later. Follow the date-alignment steps in the setup notes.

For a minimal report, add Total charge = SUM(Shipments[NET_CHARGE]), a shipment-count measure, and a month-by-month matrix. The useful result is not a fancy dashboard; it is seeing a source correction that the imported model has not yet received.

Why not filter on the last-updated timestamp?

I keep the partition filter on a stable shipment timestamp. If I partitioned by UPDATED_AT, an update could move a row into a new date interval while its old imported copy remained in an interval that was not refreshed. The business key would then appear twice.

“Detect data changes” serves a different purpose: it can use an audit column to decide which periods within the refresh range need processing. It is not a search for corrections across all archived history. Hard deletes need a separate strategy too; they do not reliably change the maximum audit timestamp.

For an older correction, I would identify the affected period, agree the backfill with the team, and explicitly reprocess it where the workspace supports that operation. Targeted XMLA processing requires an appropriate capacity or licence, permissions and a read/write endpoint. Ordinary scheduled refresh is not a historical repair button. Without that tooling, widening the policy or rebuilding the model is a planned operation with reload and deployment consequences, not something this demo performs.
