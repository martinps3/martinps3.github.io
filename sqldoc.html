sqldoc: tracing a report back to its SQL

June 2026 · 4 min read · Source on GitHub

“What's in this report?” usually sends me back to the SQL. The report name might tell me its purpose, but it won't tell me which statuses were excluded, how a field was calculated, or whether a join changes the grain. Answering properly means following the query.

I built sqldoc to make that first pass quicker. It reads a reporting query and lists its output columns, source references, joins and filters. The Python version produces Markdown or JSON; the version below runs in the browser.

Try a query

Choose a preset or replace the SQL with your own example. The output updates as you type. On a computer, hover over an output column in the diagram to highlight its source connections. The tables below contain the same references and can be scrolled on a phone.

Example

Parsing runs locally; this page does not send your query to a server. Use public or sanitised examples if your organisation restricts where work queries can be pasted.

What I wanted from the output

A useful description needs more than a list of table names. If an output column is called category, I want to know that it refers to sales.products.category_name, rather than just being told it comes from the alias p. That is the part of the output I look at first.

CTEs need their own treatment. They are intermediate steps, not physical source tables. The tool lists base tables separately and keeps intermediate references where it cannot fully resolve them. An expression involving a CTE may therefore still point to that CTE; this isn't a complete lineage engine. 

SELECT
    p.category_name AS category,
    SUM(oi.quantity * oi.unit_price) AS revenue
FROM sales.order_items oi
JOIN sales.products p ON p.product_id = oi.product_id
GROUP BY p.category_name;

Here, category has one direct source. Revenue has two inputs and an aggregation. Neither observation tells us whether the join is correct for the data. The parser doesn't connect to a database, inspect uniqueness, or execute the query.

Keeping it small has a cost

The Python tool has no third-party dependencies. I wanted something that could run where installing packages requires an approval process, even for a small documentation job. For a broader SQL transformation or lineage project, I'd start with SQLGlot instead.

Most of the care in this implementation is in the scanner. Splitting on commas is only safe when those commas aren't inside a function call, a quoted string, or a nested query. Finding a WHERE clause has similar complications: 

SELECT 'a, b' AS label
SELECT fn(a, b) AS result
SELECT *
FROM (SELECT id FROM source WHERE active = 1) s
WHERE s.id > 100
SELECT col -- WHERE is part of a comment here
FROM source

The scanner tracks quotes, comments and bracket depth so the later parsing steps can work on the relevant part of the statement. That solves a useful subset of the problem without implementing the grammar of every SQL dialect.

One bug in the Python version came from checking word boundaries around a separator that already included spaces. Splitting on " and " left two conditions together. A filter-count assertion caught it; merely checking that the parser returned a result would not have done so. Cases like that are why I care about the contents of the output, not just whether a query parses without an exception.

This is for SELECT queries. It doesn't document writes such as MERGE, separate every UNION branch, expand SELECT * without a schema, or fully trace deeply nested correlated subqueries. Check the source SQL before relying on the result.

Where it fits in a reporting workflow

I'd keep the generated documentation beside the query so it can be regenerated when the query changes. A reviewer can then see that a filter disappeared or a source table changed without comparing two long descriptions by hand.

The JSON is also useful as input to an agent writing a first draft of a report explanation. It provides a set of extracted references to work from, with the original SQL still available for checking. It cannot supply definitions such as what “delivered” means to the business. Those belong in the model documentation.
