When monthly snapshots get counted as new claims

May 2026 · 6 min read

Suppose an operations team exports its claims tracker at the end of each month. Each export contains the records being tracked at that point. Appending the files gives the team a useful history, but it also changes what a row means: one claim can now appear in several months.

If the report calls a row count “total claims,” it counts those appearances as separate claims. Summing the amount column has the same problem when the intended measure is one amount per claim. The calculations can be valid DAX and still answer the wrong question.

These are cumulative counts, not the number of open claims at month-end. At one month there are no repeated snapshots yet.

The count and the amount don't necessarily grow by the same factor. A high-value claim that stays open for several months contributes its amount repeatedly. That's one reason I check both the record count and the financial total during reconciliation.

Check the keys before changing the model

I would start with three counts. Here, SnapshotMonth is a date identifying the monthly export, and ClaimId is a non-null business key: 

SELECT
    COUNT(*) AS snapshot_rows,
    COUNT(DISTINCT ClaimId) AS distinct_claims,
    COUNT(DISTINCT SnapshotMonth) AS snapshots,
    CAST(COUNT(*) AS FLOAT)
        / NULLIF(COUNT(DISTINCT ClaimId), 0) AS rows_per_claim
FROM Claims;

A ratio above one shows repeated claim IDs, but it doesn't establish the cause. The repeats could be valid monthly observations, duplicate imports, or multiple line items belonging to the same claim. Check the proposed snapshot key as well: 

SELECT ClaimId, SnapshotMonth, COUNT(*) AS rows_at_grain
FROM Claims
GROUP BY ClaimId, SnapshotMonth
HAVING COUNT(*) > 1;

If this returns rows, investigate them before deduplicating. A tie in the latest month means a simple “take the newest row” rule could choose an arbitrary amount or status. I also check for null keys and look at a few complete claim histories, including records that disappear from later exports.

Two different reporting requirements

“What was open at the end of March?” requires historical observations. One row per claim per snapshot is useful for that question. Counts should be evaluated within a selected snapshot, and a total across several months needs a deliberate definition rather than a default sum.

“How many claims have we handled, and what is their latest known amount?” needs a claim-level table. I would normally keep the raw snapshot history and derive a second table at that grain. There is no reason to discard the history just because one report needs a different shape.

For a claim-level table

After validating that the snapshot key is unique and non-null, this query retains each claim's latest observation. It also keeps the dates of the first and last exports in which it appeared: 

WITH ranked AS (
    SELECT
        ClaimId,
        Status,
        Amount,
        OpenedDate,
        ROW_NUMBER() OVER (
            PARTITION BY ClaimId
            ORDER BY SnapshotMonth DESC
        ) AS rn,
        MIN(SnapshotMonth) OVER (PARTITION BY ClaimId) AS first_seen,
        MAX(SnapshotMonth) OVER (PARTITION BY ClaimId) AS last_seen
    FROM Claims
)
SELECT
    ClaimId,
    Status AS LastObservedStatus,
    Amount AS LastObservedAmount,
    OpenedDate,
    first_seen AS FirstSeenMonth,
    last_seen AS LastSeenMonth
FROM ranked
WHERE rn = 1;

“Last observed” is intentional. If an export contains only open claims, a claim disappearing does not tell us its final status or closing date. It could have closed, moved out of scope, or been omitted from an incomplete file. A current-state report needs another source or an agreed rule for those cases.

Similarly, FirstSeenMonth isn't necessarily the opening date, especially if the archive starts after the claim was created. Keep those meanings separate when naming fields.

For a snapshot report

Relate a snapshot-date dimension to the fact table and make the selected period visible in the report. One conservative measure is to return a count only when the context contains a single snapshot: 

Claims in Snapshot =
IF(
    HASONEVALUE('Snapshot Date'[Date]),
    COUNTROWS(Fact_Snapshot),
    BLANK()
)

This assumes an active one-to-many relationship from 'Snapshot Date'[Date] to Fact_Snapshot[SnapshotMonth] and a validated one-row-per-claim-per-snapshot grain. A chart with one snapshot per point works; an unfiltered card or a multi-month total is blank. If the business wants the latest snapshot by default, implement that explicitly and show its date rather than quietly choosing it.

Dates and reconciliation

A claim-level model can relate OpenedDate to a proper date dimension for reporting on when claims started. That is a different date role from when an export was taken. For classic DAX time intelligence, use a continuous date table covering complete years, mark it appropriately, and confirm the active relationship. Sort month names by month number, with a year-month label for charts that span years.

Before replacing the report, I would compare a small sample of claim histories, the distinct key count, and a separately calculated sum at the intended grain. Then I would check a month-end view against that month's source export. These checks answer different questions; agreement on the total alone doesn't validate the history.

If the old report was double-counting, publish the reconciliation with the change. Users will notice a lower total, and they need to know which definition changed and which previous reports are affected.
